# Release Notes 0.12.0

A release about **billing a customer with no manual work**. Until now, usage numbers only existed in the dashboard and the terminal, so handing a customer their spend meant exporting an invoice by hand. Now their own system reads the numbers directly, over HTTP, with a token that can only read.

And along with it comes the answer to a question an invoice never answered: **why that particular message cost so much**.

---

## ✨ What's New

### A customer reads their own usage, through the API

Four endpoints, four levels of detail on the same record:

| Endpoint | One row per |
| --- | --- |
| `GET /v1/usage` | time window (hour, day, week, month, year) |
| `GET /v1/usage/events` | model call |
| `GET /v1/usage/runs` | incoming message |
| `GET /v1/usage/runs/:id` | that message, call by call |

Same `Authorization: Bearer` header as the rest of the API, and each read only answers for the projects that token can reach. You can filter by project, agent, model, origin, conversation, and time window.

### A token that only reads, and never spends

Before, a token was a token: whoever had it could run the agent. If you wanted to show a customer their usage, you had to hand over a credential that could also spend your model budget.

Now a token carries permissions separate from its reach:

```bash
pepe token add --project acme --no-chat --usage --prices billable
```

That token reads usage, **cannot** run the agent, sees only the `acme` project, and sees only what the customer actually pays.

`--prices` decides how much of the numbers show up:

- `billable`: with your markup applied, what the customer pays. The default.
- `list`: the same tokens priced at the model's own rate, no markup.
- `all`: both, plus your own cost and your margin. For a token **you** keep.

The token always decides, never the request: a customer asking for `?prices=all` gets back their own token's view, not the one they asked for. And the first two are deliberately mutually exclusive, showing `billable` and `list` side by side would hand over the ratio between them, which is exactly the markup.

You can change this later without rotating the secret, so the customer's integration keeps working while what it sees changes:

```bash
pepe token permissions abc123 --prices list
```

Nothing about a token you've already created changed behavior: an existing token still can chat, and still **cannot** read usage.

### Why that message cost so much

An incoming message is rarely one model call. The agent replies, calls a tool, reads the result, calls another, replies again, and each round resends a context the previous result just grew. The per-event report counts calls, so it could never show this.

Now every call records which message it belongs to, and every message has its own record: which tools ran, how long it took, how it ended.

In the dashboard, the Usage page gained a **By message** table. Click a row and it opens into that turn's model calls, one by one. In the terminal:

```bash
pepe usage runs                 # one row per message
pepe usage runs <id>            # that message, call by call
```

The detail view shows that a message with three tools is four model calls. It's the number of calls that drives up cost, not the number of tools.

This per-message record **never stores conversation content**, which is exactly why it's kept instead of pruned like traces are. If you want content in the detail view, that's a separate permission (`--content`), off by default: a usage report is an invoice, and an invoice isn't a transcript.

## 🐛 Fixes

### One stuck reply no longer takes down the others

The system tracks every reply owed to a chat, so it can resend if delivery drops mid-way. A record saved by an older version, in a format that didn't yet have the bot's name, made this recovery sweep break **entirely**, silently: the replies owed by every other bot got lost because of a single old record. The old record is now ignored and the rest deliver normally.
