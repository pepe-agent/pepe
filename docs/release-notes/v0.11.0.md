# Release Notes 0.11.0

Hi! This version has one theme: **connecting Pepe to MCP servers that don't run on your own machine**. Along with it came a new doc page about putting Pepe on a server, two mobile layout fixes, and a fix for a test that had been keeping the release pipeline stuck.

---

## ✨ What's New

### MCP servers can now be remote

Until now, connecting to an MCP server meant Pepe **running a program** on its own machine. To reach a server hosted on the internet, the usual path was installing Node and keeping a bridge process (`npx mcp-remote`) running alongside it. On the official Docker image, that simply doesn't work: it doesn't ship Node, and the agent doesn't run as root to install one.

Now a server can just be a URL:

```bash
pepe mcp add memclaw --url https://memclaw.net/mcp \
  --header "Authorization: Bearer ${MEMCLAW_API_KEY}"
```

Same thing from the dashboard's MCP page, or by just asking the agent in conversation. From there on, nothing changes: tools still show up named `mcp__server__tool`, they're still limited by the agent's own tool list, and every call still goes through the permission prompt.

📍 *Where to use it: `pepe mcp add --url`, dashboard → MCP, or ask the agent*

### The protocol figures itself out

There are two ways a remote MCP server can talk, and the only way to know which one it speaks is to try. Pepe tries the newer one and, if the server doesn't respond, falls back to the older one. You give it the URL, and that's it.

`--transport streamable|sse` exists to pin it by hand, only for when the negotiation gets it wrong. The default is to try, because a wrong guess there looks exactly like a broken URL, and nobody should need to know that difference just to get started.

### Sign in with OAuth on servers that don't use an API key

Some hosted servers don't accept a key at all: they require you to sign in with your account. One command:

```bash
pepe mcp login memclaw
```

Pepe asks the server where its own auth service lives, registers itself there automatically, opens your browser, and stores the access it gets. Nothing to fill in by hand. If you're over SSH with no browser, it prints the link and accepts a pasted code instead, the same pattern as the model-provider logins you already use.

Access refreshes itself automatically when it's about to expire, and `pepe mcp logout NAME` forgets everything.

One detail that's deliberate: **the agent never does this login for you.** It could generate a link and ask you to click it, which is exactly the shape of a scam message. So instead it tells you which command to run, and you run it.

📍 *Where to use it: `pepe mcp login`, or the button on the dashboard's MCP page*

### Documentation: putting Pepe on a server

The Docker page always covered the container. What was missing was the next step: domain, HTTPS, and a reverse proxy. The new page brings three complete copy-paste recipes, Docker Compose with Caddy, Docker Swarm with Traefik, and Kamal, plus the four things that change once Pepe leaves `localhost` and fail silently if you forget them.

There's also a "it's not coming up, now what" table: for each symptom (name doesn't resolve, proxy 404, wrong certificate, a padlock warning), which layer actually has the problem.

📍 *Where to read it: docs → Administration → Deploying on a server*

## 🐛 Fixes

### A failing MCP tool was reported as a success

When a tool on an MCP server fails, the server can signal that *inside* a response that looks successful on the outside. Pepe only checked the outside, so it handed the error text to the agent as if it were a good result, and the agent kept building on the failure. It's now treated as an error.

### Dashboard on mobile: two fixes

The diagram showing where sensitive data flows stacked its cards and arrows against the left margin, with half the screen empty next to it. And the homepage title left the acronym "AI" alone on its own line. Both fixed.

---

## 🔧 Under the hood

- MCP servers' OAuth access now lives in Pepe's local database, not the config file. Unlike every other credential, these can't be an environment-variable reference: they rotate on their own, and nobody outside Pepe knows the current value.
- A push now triggers **one** CI run instead of two.
- A test that accepted a message meant for a different conversation had been keeping the pipeline red since July 23rd, which means that during that whole window, no release would have published an image or binaries. Diagnosed and fixed.
